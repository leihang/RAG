# 一份文档进来，会产生哪些文件、放在哪、怎么清

## 一、会产生 4 类文件

| # | 是什么 | 位置 | 一份文档对应 | 删得掉单条吗 |
|---|---|---|---|---|
| 1 | **你上传的原件** | `var/raw/<知识库 code>/<你的目录>/<文件名>`（如 `raw/main/制度/年假办法.md`） | 1 份 | ✅ 能 |
| 2 | **解析抽出的图片** | `var/parse/<doc_id>/images/*.jpg` | 0~N 张（只有 PDF/Word 等有图才有） | ✅ 能 |
| 3 | **数据库** | `var/index/ekbs.db`（+ `-wal` / `-shm`） | **全部文档共用一个文件** | ✅ 界面删除会清掉它那几行 |
| 4 | **向量** | `var/index/<分片>.faiss`，如 `kb_all_L1.faiss` | **全部文档混在同一个文件里** | ✅ 能（接口按 `chunk_id` 真删；索引是 `IndexIDMap2`） |

另外两个会长的：

| # | 是什么 | 位置 | 说明 |
|---|---|---|---|
| 5 | 上传中转目录 | `var/tmp/<upload_id>/` | 传成功会自动删；**中途放弃/失败会残留**（实测攒到过 25 个） |
| 6 | 日志 | `var/log/*.log` | `api.json.log` 已经 10 MB，只会增 |

> 生产环境把 `var/` 换成 `/data/ekbs/`，目录结构一模一样。
>
> 早先布局是 `var/raw/<sha256前16位>/…`，文件管理器里就是一堆 `95fbf1ef16573acf` 这样的壳子；
> 现已改成以**知识库 code** 开头（去重本来就在库里按 checksum 做，不依赖目录名）。
> 同名但内容不同时加 `-<sha8>` 后缀，不覆盖原件。

## 二、删文档 = 一步

界面：`/admin` → 文档管理 → 行末红色「**删除**」（输入文档名**或** `DELETE` + 填原因 ≥10 字）
批量：勾选多篇 → 「批量删除」

**一次删干净**（清 #1 #2 #3 #4）：

* 分块 + 全文索引行 + **向量**（索引是 `IndexIDMap2`，标签 = `chunk_id`，删完即回收，
  不留孤儿、也不需要"删完再重建分片"）；
* 文档记录 + 一条审计留痕；
* 磁盘上的**原件**与 `parse/<doc_id>/` 解析产物。

> ⚠️ 这是**硬删除，没有回收站**（方案 P5 要求的「软删除 + 回收站 30 天」尚未实现）。
> 删掉的文档无法在界面里恢复，只能重新导入原件。想留档就别删，或调接口时带
> `purge_assets=false`（只清库与向量、保留磁盘原件）。

**仍然会剩两样东西**，都不是 bug：

| 剩下什么 | 为什么 |
|---|---|
| `var/index/<分片>.faiss`（90 字节、`ntotal=0`） | 分片是**注册在库里的基础设施对象**（`ekbs_shard` 行 + 分片级 ACL 都指向它），不随某一份文档消失。文档删光后它就是个空壳，下次有同部门/同密级的文档进来直接复用。（实测：删完 `ntotal=0`，文件只剩索引头） |
| `var/tmp/` 里的上传残留 | 只在上传中断/失败时出现；成功上传会自己删掉 |

这两样 + 任何漏网的孤儿，都可以用扫描工具收尾：

```bash
cd /Users/lh/Documents/工作学习/AI项目/RAG
.venv/bin/python -m ekbs.tools.gc              # 先看有哪些残留（默认只报告，不删）
.venv/bin/python -m ekbs.tools.gc --delete     # 清原文件 + 图片 + tmp 残留
```

清理成功的标志：

```

parse 孤儿目录：0 个
tmp 上传残留目录：0 个
分片向量对账：
  ✅ 登记向量与实际可检索块一致，没有孤儿向量
```

## 三、全部推倒重来（清库重测）

```bash
cd /Users/lh/Documents/工作学习/AI项目/RAG
export EKBS_CONFIG=config/application.cloud.yaml
set -a; . ~/.ekbs/secrets.env; set +a

# 1) 停服务：清库时必须停，否则 api/worker/scheduler 还在写
bash scripts/dev_services.sh stop all

# 2) 先备份（出事能回滚；确认不要了就删 var/backup 里那个包）
tar czf "var/backup/pre-clean-$(date +%Y%m%d-%H%M%S).tar.gz" \
    var/index/ekbs.db var/index/*.faiss var/raw

# 3) 清空：库 + 向量 + 原件 + 解析产物 + 上传残留 + 日志
rm -f  var/index/ekbs.db var/index/ekbs.db-wal var/index/ekbs.db-shm var/index/*.faiss
rm -rf var/raw/* var/parse/* var/tmp/* var/log/*

# 4) 重建空库（29 表 / 12 审计触发器 / policy_version=1）
.venv/bin/python -m ekbs.tools.init_db

# 5) 只重建身份（部门/角色/权限/用户）——不建知识库、不灌语料、不花 token
.venv/bin/python -m ekbs.tools.seed_demo --identities-only

# 6) 起服务
bash scripts/dev_services.sh start all
```

自检 —— 库里只剩身份，没有语料：

```bash
sqlite3 var/index/ekbs.db "select 'kb',count(*) from ekbs_kb
  union all select 'document',count(*) from ekbs_document
  union all select 'chunk',count(*) from ekbs_chunk
  union all select 'shard',count(*) from ekbs_shard
  union all select 'user',count(*) from ekbs_user;"
# kb|0  document|0  chunk|0  shard|0  user|5

curl -s localhost:8000/health/deps   # vectors:0, faiss_shards:0, embed/llm/rerank:true
```

清完 `var/` 只剩：`backup index log mineru-venv parse raw run tmp`。

⚠️ 三条不要踩：

- **`var/mineru-venv` 不能删**（PDF 解析环境，2 GB，不是测试数据）。上面都是点名删，不会碰到它。
- **`rm -rf var/raw` 会连"手工放进去、还没导入"的语料一起删**；动手前 `find var/raw -type f` 看一眼。
- **别用不带参数的 `seed_demo` 代替第 5 步**：它会顺带建一个演示知识库，并把演示语料真的调云端嵌入入库（有 token 成本）。重测要的正是"0 个知识库"这个起点。

清完之后，管理台「导入」页的知识库下拉是**空的**，占位提示会写
「还没有知识库，点右边『新建』」——先点「新建」建库，再拖文件进去。
